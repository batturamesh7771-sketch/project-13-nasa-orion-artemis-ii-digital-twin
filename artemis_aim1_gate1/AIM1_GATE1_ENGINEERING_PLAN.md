# AIM 1 Engineering Plan — Build, Launch, and Handoff to the Artemis II Lunar Mission

**Status:** Gate 1 source audit and architecture proposal  
**Date:** 2026-10-20  
**Product:** one continuous Artemis II Digital Twin with three linked mission aims

## 1. Decision: what AIM 1 actually includes

AIM 1 cannot end at booster separation, or even at core-stage separation, if the aim is to transition cleanly into the existing lunar trajectory. The public Artemis II mission sequence includes early Earth-orbit operations, ICPS maneuvers and disposal, and then a translunar injection (TLI) burn using Orion's service-module main engine on Flight Day 2. NASA reported the actual TLI began at 7:49 p.m. EDT on April 2, 2026, lasted 5 minutes 50 seconds, and generated a reported 1,274 ft/s velocity change. Thus:

- **AIM 1 covers** visual assembly/rollout/pad operations, ascent, stage events, initial orbit/upper-stage operations, Orion/ICPS separation and the modeled Orion TLI burn.
- **AIM 2 begins immediately after the TLI burn** with the *same Orion state* generated by AIM 1.
- **AIM 3 begins at the simulated Earth entry interface** from AIM 2's return state.

The handoff boundary must be explicit. Do not run the AIM 2 trajectory from a separate hardcoded state after AIM 1 finishes; use an adapter to map the verified canonical state to the real existing AIM 2 input schema.

Sources: NASA Artemis II Press Kit, timeline and TLI explanation; NASA's actual Flight Day 2 TLI update. URLs are in `data/aim1_source_registry.json`.

## 2. Data truth levels

Every value must carry one of these provenance classes:

- `NASA_PUBLISHED_SPEC`: published configuration, dimensions, mass or thrust summary.
- `NASA_PUBLISHED_EVENT`: published countdown/mission-event reference, with time precision preserved.
- `CALCULATED_FROM_SOURCE`: derived using a documented conversion or formula.
- `MODEL_ASSUMPTION`: required input not located in authoritative open references; name the assumption and sensitivity.
- `MODEL_OUTPUT`: actual result of the running numerical model.
- `PUBLIC_EPHEMERIS`: result derived from an identified SPICE/Horizons ephemeris.
- `UNAVAILABLE`: not known or not currently calculated.

Never label an approximate model output as real NASA telemetry. Never label agreement with GMAT as proof that the modeled flight reproduces the exact actual flight. A visual scene for factory assembly or pad ground systems is an educational reconstruction unless backed by detailed and documented operational data.

## 3. Verified public SLS Block 1 configuration facts to seed the registry

From the 2026 Artemis II SLS Reference Guide:

- Vehicle configuration: SLS Block 1 for Artemis II, not Block 1B.
- Published height: 322.4 ft / 98.27 m.
- Published fueled mass: 5.74 million lb / 2,604 metric tonnes (rounded public reference).
- Published unfueled mass: 3.5 million lb / 1,588 metric tonnes (rounded public reference).
- Published maximum thrust: 8.8 million lbf / 39,144 kN.
- Published launch thrust: 8.27 million lbf / 36,787 kN.
- Major propulsion architecture: four RS-25 liquid engines and two five-segment solid rocket boosters; the Interim Cryogenic Propulsion Stage (ICPS) is the upper stage used for early orbital operations.
- Each booster is listed in the SLS guide at approximately 177 ft / 53.9 m high and 12 ft / 3.7 m diameter; use the full guide as the source for any further dimensions or mass figures.

These rounded summary numbers are not a complete state-dependent mass model. In particular, do not construct engine/booster thrust-time curves from a single total thrust figure. A numerical ascent simulation also needs stage/component mass histories, thrust-vs-time, effective exhaust velocity or specific impulse, aerodynamic force coefficients, reference area, guidance/pitch steering, and time-dependent configuration data. Each parameter must be found in a suitable authoritative public source or explicitly modeled as uncertain.

## 4. Official event checkpoints and their interpretation

NASA provides a preflight Press Kit timeline and a launch-day public event update. Some event times differ by seconds. Keep both records: preflight planned time is not identical to a reported launch-day reference. The day-of page says times may vary by several seconds, so do not assert precision better than that source supports.

Selected launch-day published ascent references:

- tower-clear / roll-pitch maneuver: T+7 s;
- supersonic: T+56 s;
- maximum dynamic pressure: T+72 s;
- solid booster separation: T+129 s;
- launch abort system jettison: T+193 s;
- core stage main-engine cutoff: T+482 s;
- core-stage separation from ICPS/Orion stack: T+494 s.

Preflight press-kit reference values differ for several events (for example max-Q +70 s, booster separation +128 s, LAS jettison +198 s, core MECO +486 s, core separation +498 s). Preserve this difference rather than merging the values or tuning an ODE secretly to make every number appear exact.

The press kit also lists later milestones including ICPS nozzle extension, solar array deployment, perigee-raise and apogee-raise maneuvers, Orion/ICPS separation, ICPS disposal, and planned TLI. The actual TLI report is a better reference for the completed TLI event: NASA says 7:49 p.m. EDT on April 2, 2026; 5 minutes 50 seconds; reported delta-v 1,274 ft/s. Converted value is approximately 388.3152 m/s (conversion from the published figure, not a claim about the exact vector).

Use these events for event/state consistency checks, not as substitutes for continuous truth-state data. Public event times alone cannot determine full position, velocity, attitude, mass, or actual aerodynamic loads at each event.

## 5. Recommended software architecture

### A. Keep the existing server and AIM 2/AIM 3

First inspect the current repository. Identify the actual numerical engine, existing state schemas, trajectory provider, server routes and dashboard component names. Preserve existing AIM 2 code and the repaired UI. Create `simulation/aim1/` or an equivalent bounded module that fits the repository rather than scattering launch physics throughout frontend files.

Recommended separation:

1. `reference_data`: source registry, versioned vehicle configuration, public timeline events.
2. `assembly_scene`: deterministic visual scene-state machine (factory/VAB/rollout/pad/countdown).
3. `ascent_dynamics`: numerical equations for launch/ascent, with a configuration/model version.
4. `event_manager`: event detection and discrete stage/configuration transitions.
5. `orbital_operations`: initial orbit and ICPS/Orion operations through TLI, with clearly declared assumptions.
6. `handoff_adapter`: maps AIM 1 post-TLI state into AIM 2's actual input structure, with unit/frame conversion tests.
7. `aim1_api`: mission state and event output through the existing API/WebSocket protocol.
8. `validation`: numerical checks, NASA event comparison, integration tests and GMAT orbital benchmarks.

### B. Use a staged dynamical model

**Stage 0 — assembly and launch-pad scenes.** These are documented 3D/sequence reconstructions. The vehicle components should be dimensionally credible and identified; scene transitions must follow a versioned event script. This stage is not a manufacturing-process simulation unless actual process models are supplied.

**Stage 1 — ascent 3-DOF point-mass model.** Start with a transparent inertial translational model and explicit mass/thrust configuration. Use an appropriate adaptive integrator (e.g., SciPy `solve_ivp` with DOP853, or the engine already used by the project). Include Earth gravity, Earth rotation in launch-site initial velocity/frame conversion, atmosphere, aerodynamic drag, thrust-vector direction/pitch guidance as configured, and mass flow. Detect tower-clear, max-Q, booster separation, LAS jettison, core MECO, and core separation. Each stage event changes active mass, propulsion, geometry/reference area as applicable. Do not animate position separately from the computed state.

**Stage 2 — 6-DOF enhancement only when inputs justify it.** Six-degree-of-freedom flight requires mass properties/inertia, aero coefficients and moment coefficients, center-of-mass/reference positions, thrust vector control/gimbal, wind and atmosphere inputs, and a valid control law. NASA's `simupy-flight` provides an open-source Python flight-dynamics framework and NESC 6-DOF test cases for generic equation verification; it is useful as a verification reference, but it is not an SLS model and does not validate our SLS parameters. Evaluate it before adding bespoke 6-DOF math. Do not jump to SLS CFD to fill missing inputs.

**Stage 3 — early orbit and TLI.** After booster/core-stage sequence, propagate through applicable ICPS and Orion maneuvers with mass/thrust histories and documented assumptions. Model Orion/ICPS separation and disposal only at the corresponding events. At the actual TLI epoch, the Orion service-module burn changes its velocity according to the model. The next state delivered to AIM 2 is the post-burn Orion/ESM state—not the stack's state at core-stage MECO.

### C. Force model

At minimum for the 3-DOF stage, define the state and units and implement:

- translational kinematics: `dr/dt = v`;
- force balance: `dv/dt = (T_vector + F_aero)/m + g` in the chosen inertial frame;
- continuous propellant mass flow where a documented finite-burn engine model is active;
- discontinuous mass/configuration reset at staging/jettison events;
- rotating-Earth surface initial velocity using the declared Earth orientation/rotation convention;
- atmospheric-relative velocity for drag and dynamic pressure;
- event outputs for altitude, speed, Mach, dynamic pressure, mass, acceleration and event time.

Use dimensionally consistent SI internally. Every force/parameter data row must document unit, source, validity, and uncertainty/assumption. Validate no division-by-zero or discontinuity handling errors at liftoff and staging. Model SRB and RS-25 thrust curves separately if authoritative curves are available; otherwise do not invent detailed curves or claim flight fidelity. A total initial thrust summary alone can only support a coarse aggregate model.

### D. Physics tools and what they do not prove

- **Python + SciPy:** primary integration engine and testable calculation path.
- **NASA GMAT R2026a:** independent cross-validation for compatible orbital arcs, orbit states, maneuvers and propagation settings. It does not independently validate low-altitude SLS combustion, SRB grain burn physics, wind loads, launch-pad clearance, detailed aerodynamics or structure/separation dynamics.
- **NASA `simupy-flight`:** useful flight-dynamics implementation and NESC test cases to cross-check generic 6-DOF equations; not an SLS vehicle model.
- **NAIF SPICE/JPL Horizons:** suitable ephemeris sources for Earth/Moon geometry and later mission frames; must verify coverage, center, frame, time scale, kernels and units.
- **NASA SLS Block 1 3D model + Orion 3D model:** geometry/visualization assets. They do not provide engineering dynamics parameters. Review each asset and usage/attribution rules.
- **OpenMDAO/Dymos:** optional later if guidance/trajectory optimization is required; not mandatory for the first numerical ascent version.
- **Basilisk:** optional for spacecraft attitude/GNC in later spacecraft-specific work; not the primary SLS booster/aero model.
- **CFD tools (SU2/OpenFOAM):** not a Gate 1/initial ascent requirement; only consider if a justified aerodynamic research task and suitable geometry/boundary conditions exist.

## 6. Validation strategy and acceptance gates

### Gate A — traceability

- Every loaded parameter has a source ID, unit, configuration version, time/phase validity, and truth class.
- No source-free numeric parameter is silently treated as verified.
- Published planned event times and launch-day-published event times remain separate.

### Gate B — mathematical correctness

- Unit tests for equations and units.
- Analytical limits (constant-acceleration/no-drag test, vacuum point-mass checks, and variable mass/thrust checks where applicable).
- Integrator convergence study over multiple tolerances/max-step configurations.
- Mass conservation/accounting through burns and separations.
- Force and acceleration dimensions verified.
- Event root-finding and mass/vehicle configuration reset tests.
- Rotating Earth/site-state transform tests.
- Regression against NASA NESC test cases if `simupy-flight` is adopted or used as a reference.

### Gate C — NASA public reference comparisons

- Compare event times to the relevant NASA reference, preserving the reference's uncertainty/precision. Report residuals in seconds.
- Compare the dynamic model's altitude/speed/max-Q history with a sourced public curve only if the actual curve/table and data are obtained. Do not fabricate a curve from a few events.
- Show sensitivity of event times and orbit insertion to uncertain thrust, mass and aero parameters.
- Calibrating a model to published milestones is not independent validation; report it as calibration and keep separate validation data if available.

### Gate D — GMAT

- Export AIM 1's modeled post-insertion/orbit state to GMAT at a common epoch/frame/unit basis.
- Compare the orbit-only propagation segment under matching force models.
- Then compare the next AIM 2 initial trajectory propagation from the canonical handoff state.
- Report full `dr`, `dv` vector residuals and norms at common epochs, force models, solver settings, unit/frame conversions and version logs.
- Do not use GMAT as a test of low-altitude powered ascent.

### Gate E — continuous mission and UI

- Timestamps are monotonic; events trigger only once; pause/seek/reset cannot corrupt numerical state history.
- The same state object drives dashboard telemetry and Three.js pose/trajectory.
- Stage events remove the relevant component from the parent stack and create a detached-body visual state; any detached-body ballistic motion is only modeled if a dynamics model exists, otherwise mark its subsequent path as illustrative.
- Handoff's position, velocity, mass, epoch, frame and provenance are tested end-to-end.
- Start, pause, resume, reset, seek, full mission playback and source/validation panels work in the real browser.

## 7. What public data cannot establish by itself

Public reference guides and milestones provide strong constraints, not every SLS flight-state time history. Unless exact public inputs are located, do not claim exact reconstruction of:

- instantaneous per-engine/booster thrust versus time;
- grain burn geometry or detailed booster internal ballistics;
- exact propellant mass flow and stage/component mass histories;
- high-fidelity SLS aerodynamic coefficients and moments through Mach/angle-of-attack regimes;
- real-time atmospheric winds and upper-air conditions for the actual launch;
- full stack inertia tensors, flexible-body modes and control-system code;
- detailed hold-down/umbilical mechanical dynamics;
- full-resolution historical NASA flight telemetry and guidance commands.

If not available, implement a reduced-order research simulation with explicit model assumptions and uncertainty analysis. It can be mathematically correct under its assumptions without being an exact real-flight reconstruction. That distinction must appear in the UI and final report.

## 8. First implementation deliverable

AIM 1's initial deliverable should not be a broad new rewrite. Deliver:

1. a repository audit identifying actual AIM 2 input schema and routes;
2. parameter source registry and public event timeline loaded from JSON;
3. assembly/rollout/pad scene-state machine, visually separate from the numerical simulation;
4. launch/ascent model with tests and stated fidelity class;
5. early-orbit/TLI event sequence with modeled post-TLI state handoff;
6. GMAT-compatible orbit export and actual comparison report;
7. integrated browser screenshot and pass/fail matrix.

Do not expand to more complex simulation before the model input data, state handoff and verification gates are working.
